# 岗位匹配与经历表达

## 选择结构

没有实习不代表没有经历：先挖掘课程设计、毕业设计、竞赛、个人作品、社团实践、兼职或开源贡献，保留其真实性质。不要为了凑齐栏目写空章节。

| 情况 | 常见栏目顺序 | 篇幅重点 |
| --- | --- | --- |
| 应届生/实习 | 教育 → 技术栈 → 项目/实习 → 其他；较强实习可优先 | 岗位相关实践、可验证的能力 |
| 社招 | 简介（可选）→ 工作 → 项目（必要时）→ 技能 → 教育 | 最近岗位、个人贡献、结果 |
| 转行 | 简介（可选）→ 相关实践 → 可迁移的工作成果 → 技能 → 教育 | 用实际产出证明新方向能力 |
| 设计/内容岗位 | 简介（可选）→ 实践/项目 → 作品集 → 技能 → 教育 | 作品链接、受众、本人职责 |

每段核心经历使用完整短段落或 2–5 个有信息量的条目，按事实丰富程度展开。用户只提供一句参与描述时，优先按 [经历扩写方法](experience-expansion.md) 补问；不能默认该句已经足够。确实内容有限且用户选择直接输出时，可保留较短事实稿并说明限制。日期一般倒序，内容按对目标岗位的价值排序。

## 建立岗位证据映射

将岗位要求分为核心职责、硬性要求、加分项，分别标为“有证据”“部分支持”“暂无证据”。这个表用于改写判断，不默认放入简历，也不转换成伪精确匹配分数。

例如岗位要求 SQL：用户实际用 SQL 进行周报统计，可写使用场景；仅看过课程则写“学习过 SQL”或省略，不能写“熟练掌握 SQL”。证据缺口可转为学习建议，不能转为经历事实。

## 条目改写

优先表达“动作 + 对象 + 方法 + 结果”，允许结果为交付物而不是数字。用 STAR 分析原材料，但不在简历里机械标注 Situation/Task/Action/Result。

以下例子是假设材料已提供对应事实，不能直接移植到用户履历：

- 原描述：“参与后台开发。” → 有对应事实时：“负责订单查询接口开发，使用 Spring Boot 完成分页与条件筛选，并补充接口文档及测试用例。”
- 原描述：“整理报表。” → 有对应事实时：“使用 Excel 透视表整理每周销售数据，形成按产品和区域拆分的周报，供团队例会复盘。”
- 原描述：“团队转化率提升。” → 先确认：“你负责哪部分，变化是否由你的工作带来，统计口径是什么？”无个人归属依据时，仅写其负责的实验、分析或交付物。
- 原描述：“完成推荐系统项目。” → 区分课堂离线实验与线上部署，补充算法选择、本人模块、数据来源和验证方式；没有真实部署，不写“服务线上用户”。

避免“精通所有技术”“抗压能力强”“责任心强”等无证据的评价。技术堆栈融入具体工作，技能列表做简要汇总。每个条目应能回答面试追问：为什么这样做、本人做了什么、结果如何验证。

技术栈按语言、框架、数据库、工具等合并成紧凑分组，说明用户确实使用过的能力范围。不要写“编程语言 | Java”“数据库 | MySQL”后就结束，也不要未经确认从技术名称升级成“熟练”。核心技术、方法、模块和已确认结果可通过 `emphasis` 局部加粗，通常每条不超过 2–3 处，不把整个段落标为重点。

## 翻译和一致性

英文使用简洁动词开头，保持时态与任职状态一致；不机械逐字翻译中文句子。机构名称、学位、日期、数字及链接与中文稿一致。没有官方英文名时保留原名，或使用清楚标注的解释性译名；不把参与翻译成 Led，不把课程项目翻译成 Internship。

检查姓名和联系方式、教育状态、日期先后、技术名称、百分比口径、同一项目重复归因、内容保密要求。不要用模板自带的虚构成就替换缺失内容。

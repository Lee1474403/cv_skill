# 项目与实习的深度改写

## 先分清资料简略与经历简单

一句“参与用户权限模块开发”通常意味着尚未采集技术和职责细节，并不意味着候选人只值得一行描述。不要直接原句搬运到正式成品。一次提出该经历最关键的 3–5 个问题，允许口述或贴项目说明、代码片段、课程报告，不要求量化指标才能继续。

针对权限模块，可问：使用什么框架；个人负责哪些接口或业务流程；角色和权限如何关联；如何鉴权和处理越权；做过什么测试、联调或文档。针对图书借阅系统，可问：服务谁；实现哪些功能；个人负责哪些模块；用了哪些技术；遇到什么问题并如何处理；最后交付了什么。

这些都是询问方向，不是已知事实。不能默认权限模块必然使用 RBAC、Spring Security、JWT 或 Redis，也不能把候选人的技能列表当作每个项目实际采用的技术栈。

## 把事实展开成阅读者能理解的贡献

完整描述通常覆盖下列维度中的 3–5 个，篇幅由真实信息量决定：

1. 业务背景：面向什么人、什么业务或课程目标。
2. 本人职责：负责什么模块、边界、与团队如何分工。
3. 实现方法：技术、数据流、流程设计或具体操作。
4. 关键问题：遇到的限制和已采取的处理办法。
5. 验证与交付：功能测试、联调、演示、文档、部署或测量结果。

对核心项目，可写 1–2 个完整短段落，或 3–5 条有内容的贡献；材料充分时通常约 100–200 个中文字符或更多，不能以字数机械合格。实习通常 2–4 条，约 80–160 字；复杂相关实习可以更长。这些是密度参考，不是必须凑出的字数。

段落可组织为“项目背景／核心实现／工程验证”，条目可用“权限实现：”“接口联调：”等短标签。避免每个项目都重复相同标签，也避免把一句话硬拆为三条。

## 可润色与需确认的边界

| 操作 | 处理方式 |
| --- | --- |
| 改善动词、术语、逻辑和阅读顺序 | 直接进行 |
| 把已有事实拆成职责、方法和交付，合并散落在材料中的证据 | 直接进行，内部记录来源 |
| 解释已明确业务的基本场景 | 可以补简短背景，不扩大用户范围、部署规模和职责 |
| 增加具体框架、模块、算法、测试、部署、故障处理 | 来源明确才加入，否则追问 |
| 增加数字、改为负责人、声称上线或高并发 | 需要明确证据，不能以“美化”替代事实 |
| 参考简历中的“显著提升”“达到行业标准”等措辞 | 只有候选人自己的证据支持时才能使用 |

事实不够时先给可确认的改写预案，说明哪几个补充将使经历完整。未经确认的建议放在对话中或独立工作稿，不能写进正式履历。用户明确要求跳过补问时可以导出事实受限版，并说明核心经历仍缺少具体贡献；不能称其已完成深度优化。

## 有补充事实的改写示范

以下完全虚构，仅示范改写方法：

原句：“参与用户权限模块后端开发。”

用户补充：使用 Spring Boot 和 MyBatis；本人做角色与权限关联接口、分页查询和重复关联校验；参与前后端联调；没有可提供的性能数字，也不是模块负责人。

可改写：

> 参与用户权限模块的后端开发，使用 Spring Boot 与 MyBatis 实现角色、权限关联及分页查询接口，补充重复关联校验与异常返回。配合前端完成接口联调，整理接口参数和使用说明，支持权限配置功能的验证与交付。

不可改写：“独立主导企业级 RBAC 架构，使用 Redis 实现权限缓存，使百万用户场景性能提升 80%。”

第二例：只知道“图书借阅管理系统，大二课程项目”，此时问本人做了哪些功能、技术和验证方式；不要擅自加入借阅归还接口、库存扣减、逾期处理、事务或压力测试。

## 内容完成门槛

逐段检查核心经历是否写明本人动作、具体对象、至少一种方法或可核验交付。仅有项目名称、时间、职位或“参与开发”不达标。不得用一页成品替代必要的补问。

生成器的内容检查用于发现过短条目，不证明真实性或写作质量。告警后应回到信息采集与改写，再排版；只有用户选择事实受限版本时才使用 `--allow-sparse`。模板示例中的丰满经历不能作为真实候选人的补全数据。
